# 1. Идентификация существующих и потенциальных проблемных мест

1. **Single Point of Failure в инфраструктуре**
    - Каждое приложение имеет только один инстанс
    - Базы данных работают в режиме single instance (одна нода для записи и чтения)
    - Отсутствие отказоустойчивости может привести к полной остановке бизнеса

2. **Проблема с потерянными заказами**
    - Клиенты не получают заказы или работа над ними затягивается на месяцы
    - Нет визуализации узких мест в обработке заказов
    - Отсутствие мониторинга SLA по статусам заказов

3. **Расчет стоимости**
    - Синхронный вызов блокирует API, расчет занимает 2-3 минуты (до 30 минут для сложных моделей)
    - Один инстанс MES API может не справиться с нагрузкой
    - Возможны таймауты и потеря заказов

4. **Производительность дашборда MES**
    - Долгая загрузка первой страницы с заказами
    - Пагинация и фильтры не решили проблему
    - Операторы не могут эффективно выбирать новые заказы

5. **RabbitMQ как Single Point of Failure**
    - Единственный канал интеграции между MES и CRM
    - Отсутствие информации о надежности и настройках (persistence, acknowledgments)
    - Риск потери сообщений о заказах

6. **Отсутствие observability**
    - Нет упоминания о логировании, трейсинге, метриках
    - Невозможно быстро диагностировать проблемы в production
    - Нет алертинга о проблемах

7. **Медленный процесс QA и релизов**
    - Ручное E2E тестирование замедляет релизы
    - Задержки релизов растут (раньше до месяца, теперь больше)
    - Один QA-инженер не справляется с нагрузкой

8. **Недостаточная масштабируемость инфраструктуры**
    - Линейный рост заказов (+100/месяц) не учтен в архитектуре
    - Производственные мощности есть, но софт не справляется

9. **Хранилище 3D файлов как потенциальное узкое место**
    - S3-based storage, но нет информации о лимитах и производительности
    - Файлы используются несколькими компонентами (Shop API, MES API, CRM API)

10. **Отсутствие изоляции между B2C и B2B трафиком**
    - API пользователи и клиенты онлайн-магазина используют одни инстансы
    - Проблемы в API-канале влияют на основной бизнес

11. **Отсутствие rate limiting и throttling на API**
    - После открытия API "завалило заказами"
    - Нет защиты от непреднамеренной перегрузки


12. **Недостаточная информация о состоянии заказа**
    - Нет уведомления клиентов
    - Отсутствие прозрачности процесса

# 2. Инициативы для устранения проблем

**1. Внедрение горизонтального масштабирования приложений**
- Развернуть минимум 2 инстанса каждого приложения за load balancer

**2. Обеспечение высокой доступности баз данных**
- Настроить PostgreSQL в режиме master-replica (read replicas)
- Разделить read/write запросы на уровне приложения
- Настроить автоматический failover

**3. Обеспечение отказоустойчивости RabbitMQ**
- Развернуть RabbitMQ cluster 
- Настроить mirrored queues для критичных очередей
- Включить publisher confirms и consumer acknowledgments

**4. Внедрение системы мониторинга**
- Централизованное логирование (ELK stack)
- Distributed tracing (Jaeger)
- Мониторинг и алертинг (Prometheus + Grafana)
- Дашборды для бизнес-метрик

**5. Асинхронный расчет стоимости через очереди**
- Перевести расчет стоимости в асинхронный режим
- MES получает задачу на расчет через RabbitMQ
- Клиент получает response немедленно с идентификатором задачи
- Приоритетные очереди для B2C vs B2B

**6. Оптимизация дашборда MES**
- Внедрить кэширование данных (Redis)
- Оптимизировать SQL запросы (индексы, денормализация)

**7. Внедрение read replicas для read-heavy операций**
- CRM API читает из read-replica
- Shop API читает каталог из read-replica
- MES дашборд читает из read-replica

**8. Оптимизация работы с 3D файлами**
- CDN для раздачи файлов
- Кэширование результатов расчета для похожих моделей

**9. Внедрение API Gateway**
- Rate limiting и throttling
- API versioning
- Аутентификация и авторизация для API клиентов
- Мониторинг использования API

**10. Изоляция B2B и B2C трафика**
- Отдельные инстансы приложений для API клиентов
- Отдельные очереди в RabbitMQ
- Изоляция на уровне базы данных (схемы или отдельные БД)

# 3. Инициативы в порядке приоритета

## Целевая архитектура через полгода
- **Мониторинг**: полная observability стека (логи, метрики, трейсы)
- **Высокая доступность**: все компоненты работают в режиме HA (минимум 2 инстанса)
- **Кэширование**: Redis для горячих данных
- **Асинхронная обработка**: расчет стоимости через очереди
- **API Gateway**: централизованное управление API

## Выбор TOP-3 инициатив:

### 4. Внедрение системы мониторинга
**Почему первое:**
- Без visibility мы не можем диагностировать проблемы
- Даст понимание, где именно теряются заказы
- Покажет узкие места в производительности
- Позволит измерить эффект от других инициатив

###  5: Асинхронный расчет стоимости через очереди
**Почему второе:**
- Решает критическую проблему потери B2B клиентов
- Устраняет блокировку API на 2-30 минут
- Улучшит UX для B2C клиентов
- Позволит масштабировать расчеты независимо

#### 1 Горизонтальное масштабирование + 3 Обеспечение отказоустойчивости RabbitMQ
**Почему третье:**
- Устраняет все single points of failure
- Обеспечивает надежность системы
- Позволяет выдержать рост нагрузки
