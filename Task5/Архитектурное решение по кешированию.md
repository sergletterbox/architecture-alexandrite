# Мотивация

Shop API - каталог готовых изделий
Проблема: растущая нагрузка на систему из-за новых рынков
Решение: кешировать список товаров на уровне фронтенда и Redis на бэкенде, TTL: 1 час

MES - результаты расчёта стоимости
Проблема: расчёт занимает 2-30 минут, нагрузка выросла из-за API-клиентов
Решение: кешировать результат расчёта по хешу 3D-модели (идентичные модели дают одинаковую цену), TTL 24-48 часов

MES API - список заказов для операторов
Проблема: медленная загрузка дашборда с фильтром по статусам, операторы не видят новые заказы вовремя
Решение: кешировать агрегированные данные о заказах по статусам с TTL 10-30 секунд, инвалидация при изменении статуса

# Предлагаемое решение 

Shop API - каталог товаров: клиентское + серверное кеширование
Клиентское (HTTP cache): статичный контент, редкие изменения каталога, снижаем нагрузку на бэкенд
Серверное (Cache-Aside Redis): защита БД от нагрузки при промахах
Комбинация обеспечивает минимальную latency и защиту от spike'ов трафика

MES - расчёты стоимости: серверное кеширование (Cache-Aside)
Расчёт дорогой (2-30 минут), результат неизменен для идентичных моделей
Cache-Aside идеален: кешируем только рассчитанные модели, промах кеша = запуск расчёта

MES API - список заказов: серверное кеширование (Cache-Aside)
Данные часто читаются (операторы постоянно обновляют список)
Cache-Aside позволяет кешировать только востребованные фильтры

# Инвалидация 

 - Shop API. Временная инвалидация как наиболее простое решение, небольшая задержка в обновлении каталога не критична.
 - MES API. Инвалидация по ключу: при изменении статуса заказа инвалидировать кэш с указанным orderId, временная инвалидация для fallback
